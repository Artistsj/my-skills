# 档案管理（文书定）-解决方案-综合档案-业档一体架构框架

## R — 原文 (Reading)

> "前端业务系统当中的电子文件按照收集保管范围表，应收尽收、应归尽归，
> 实现了包括公文档案一体化、人事档案一体化、合同档案一体化等在内的
> 全门类场景业档一体化管理。具有强大的集成引擎，通过配置化的方式
> 让业务系统集成对接更便捷，让电子档案100%自动归档，而且归档的文件
> 根据权限可以被业务系统安全调用。"
>
> — 泛微文书定，第46页·核心亮点·100%归档赋能业务

---

## I — 方法论骨架 (Interpretation)

业档一体不是简单的"把业务数据导入档案系统"，而是将档案管理流程与前端业务流程从设计阶段就深度融合，形成双向闭环：

正向链路——业务系统产生电子文件，在流程办结节点按照预定义的归档范围、元数据映射和分类规则，自动封装成标准归档信息包，通过集成引擎推送到档案系统，档案系统接收后执行四性检测、自动分类、自动组件，完成归档。

反向链路——归档后的档案数据不是封存起来，而是根据权限可以被业务系统安全调用，支撑业务查询、审计、决策，让档案从"死数据"变成"活资产"。

核心支撑要素：收集保管范围表（明确哪些该归）、元数据对照表（字段映射）、集成引擎（配置化对接）、预归档平台（缓冲层）。

## A1 — 书中的应用 (Past Application)

### 案例 1: 公文管理"业档一体"
- **问题**: 公文从拟稿到分发全流程在公文系统完成，但归档需要人工导出再导入档案系统，效率低且容易出错
- **方法论的使用**: 公文系统办结后，自动将版式文件+元数据封装成归档信息包，通过标准接口传输到档案系统，档案系统接收时执行四性检测
- **结论**: 公文归档全流程自动化，无需人工二次整理
- **结果**: 确保公文档案的完整性和合规性，档案员从操作员变成审核员

### 案例 2: 会计报销入账归档"三单合一"
- **问题**: 财务凭证、报销单、发票、银行回单分散在不同系统，审计时需要在多套系统中切换查找
- **方法论的使用**: 报销全流程产生的所有单据（记账凭证+报销单+发票+银行回单）通过接口自动归档，并按业务逻辑自动关联匹配
- **结论**: 实现"三单合一，单单匹配，关联查询"
- **结果**: 财务人员查询审计效率大幅提升，避免在多套系统中切换

### 案例 3: 人事管理"一人一档"
- **问题**: 员工从入职到离职产生的人事文件散落在各个HR流程节点，档案归集困难，缺件难发现
- **方法论的使用**: 员工每个业务流程办结后，相关附件通过接口自动归档到对应的人员档案条目下，形成"一人一档"
- **结论**: 人事档案随业务流程自动归集，缺件自动提醒
- **结果**: 确保员工档案完整准确，人事档案管理效率显著提升

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 企业规划档案信息化建设，需要设计业务系统与档案系统的整体融合架构时
2. 某个业务系统（如OA/ERP/合同/HR/财务）需要对接档案系统实现自动归档时
3. 讨论"为什么档案要和业务一体化"、"业档一体怎么做"这类方案设计问题时
4. 评估现有档案系统与业务系统的集成方案是否合理时

### 语言信号 (用户的话里出现这些就应激活)

- "业档一体" / "业档融合" / "业务档案一体化"
- "业务系统怎么对接档案系统"
- "自动归档怎么实现"
- "档案系统和OA/ERP怎么集成"
- "100%自动归档"
- "档案数据反哺业务"

### 与相邻 skill 的区分

- 与 `archives-pre-archiving` 的区别：业档一体是宏观架构框架，讲的是整体融合方案；预归档是其中的一个具体机制（缓冲层），讲的是收集前置化的操作方法
- 与 `archives-lifecycle` 的区别：业档一体关注的是"业务系统↔档案系统"的横向融合；全生命周期关注的是"收管存用"的纵向流程
- 与 `archives-four-tests` 的区别：四性检测是业档一体链路中的一个质量控制节点，不是架构本身

## E — 可执行步骤 (Execution)

当 skill 被激活后，agent 应按以下步骤执行:

1. **梳理归档范围和保管期限**
   - 完成标准：输出"收集保管范围表"，明确每个业务场景下哪些文件需要归档、保管期限是多久
   - 判停条件：若用户还没明确有哪些业务系统，先做业务系统盘点

2. **定义元数据映射规则**
   - 完成标准：输出"元数据对照表"，明确业务系统的每个字段对应档案系统的哪个元数据字段，以及转换规则
   - 判停条件：若档案系统尚未定义门类和元数据，先做档案门类规划

3. **设计归档触发节点**
   - 完成标准：明确每个业务流程在哪个节点触发归档动作（如审批完成后、办结后、月结后），以及是实时归档还是定时批量归档

4. **规划集成对接方式**
   - 完成标准：确定集成方式（标准REST接口/中间件/预归档平台）、数据格式（版式文件+元数据封装/EEP数据包）、错误处理机制

5. **设计档案反哺业务的路径**
   - 完成标准：明确归档后哪些档案数据可以被业务系统调用、调用方式（API/嵌入页面）、权限控制机制

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯档案管理内部操作问题（如怎么组卷、怎么著录、怎么借阅）——用全生命周期框架或利用控制框架
- 纯技术集成实现问题（如接口怎么写、用什么ESB）——这是开发团队的事，不是架构方法论
- 企业完全没有信息化系统、全是纸质文件的场景——业档一体的前提是有业务系统

### 作者在书中警告的失败模式

- 传统模式下"业务系统归业务系统，档案系统归档案系统"的孤岛模式，导致档案收集难、整理难、利用难
- 业务与档案脱节，档案数据封闭，难以融入业务，价值难体现

### 作者的盲点 / 时代局限

- 作者是产品厂商，天然倾向于"集成引擎能解决一切"，但实际落地中业务系统改造的难度和成本可能远超预期
- 假设企业已有完整的、可对接的前端业务系统，且这些系统支持标准API接口——这对很多中小企业不成立
- 对组织变革和人的因素考虑不足：业档一体要求业务人员也参与归档工作，这需要管理制度和文化的配合，不是光靠技术能解决的

### 容易混淆的邻近方法论

- 不要和"系统集成"混淆：业档一体不是纯技术集成，而是业务流程与档案流程的融合，包含管理模式的调整
- 不要和"数据同步"混淆：业档一体不是简单的数据搬运，而是有归档规则、元数据转换、质量检测、分类组件的完整归档链路
